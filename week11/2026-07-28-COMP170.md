## Counting Words the Hard Way, on Purpose

Picking up from yesterday, we started writing the actual word-counting program against the opening lines of *A Tale of Two Cities*, deliberately plain — no methods yet. We built two matching lists side by side: one holding each unique word, one holding how many times we'd seen it, with position in the list being the only thing tying a word to its count. We named this "array synchronization" and were upfront that it's a fragile technique, kept alive here only to show why we'll want something better.

## Reading the File, Word by Word

We opened the file, read it one line at a time, and used the `split()` method to break each line into individual words wherever a space appears. For every word, we searched our list of words seen so far: if it was already there, we bumped its matching count up by one; if not, we added the word and started its count at one.

## A Broken First Draft, Kept as `bad_logic_example.py`

Our very first version crashed before it could count a single word. We set a flag called `is_unique` to `False` to mean "haven't decided yet," then used that same flag directly as the condition for continuing to search (`while i < len(contents) and is_unique`). Because it started `False`, that condition was false immediately, so the search loop never ran — not once, for any word. `i` stayed at `0`, `is_unique` never changed, and the `if`/`else` branches meant to add new words or bump existing counts never got a real chance to run correctly either: the very first word fell into the branch that updates `frequency[i-1]`, which meant `frequency[-1]` on a still-empty list, and the program crashed with an `IndexError`. We left this version exactly as broken as we found it and saved it separately as `bad_logic_example.py`, so it stays in the repository as a concrete example of how getting a loop's stopping condition backwards doesn't just break the loop — it silently breaks everything downstream that depended on the loop actually running.

## Two Bugs, Two Lessons

After rewriting the search with a `found` flag instead of `is_unique`, the logic ran, but we still hit a real off-by-one bug — after finding a match, our search had already moved one position past it, so the code needed to look back one spot to update the right count. We also caused an infinite loop by checking for the end of the file the wrong way (an empty line and "nothing left to read" aren't the same thing), fixed by checking the line's length instead.

## Normalizing and What's Next

We noticed "It" and "it" were being counted separately, so we converted every line to uppercase before counting, which changed our unique-word count only slightly for these three paragraphs. Tomorrow we'll handle punctuation and singular/plural word forms, then retire the two synchronized lists in favor of a single, safer dictionary.
